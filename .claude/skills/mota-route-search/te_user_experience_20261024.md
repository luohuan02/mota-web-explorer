## 三、为什么之前没探到这些优化(漏探根因,必读)

### 根因 1:算子粒度缺口——微交换与转换时点

- **32F 先宝石再拿剑**(-6 dmg):相邻两次拾取的顺序交换。我们的 unit 重排算子只在
  41301 族尾段一次性跑过(AgentH 852 候选),从未作为**每条转换后 walk 的标准后处理**;
  converter 逐格保序,永不交换;6 HP 量级又常被 beam 剪枝阈值过滤。
  人类玩家看见"先吃 buff 再打怪"天然就会换序。
- **38F 200→3yk 延后到魔龙后**:商人的两个搜索维度——**次数**与**时点**——我们只搜过
  次数(def-defer 也只对防商店做过)。延后窗口合法性 = 窗口内没有门/战斗需要这 3yk
  且购买力不变;收益 = 保住 2120 金币悬崖(魔龙后金币必死,换钥匙白赚)。

**未来算子规格**:
- `OP-SWAP`:每条 walk 生成后自动跑一遍 visit 段内相邻对交换(A、B 无键/门/阈值依赖即
  可换),dmg 严格更低才保留;注意 auto_sweep 归属。
- `OP-DEFER`:每个转换节点(商店/商人/交易)枚举向后推迟,直到其产出(钥匙/金币/属性)
  首次被需要或购买力断裂为止;重点跨 boss 边界(终局死金币)。

### 根因 2:血统锚定 + 分区出口规格写死

- 我们的 zone1 封闭(vc5/MT9 蓝门定理)以 41301 血统的下游需求为前提(exit yk≥4/bk≥1
  零缺口),据此判 9 楼蓝门+7 楼省 2yk「联合不可行」。用户 41477 恰好用这个组合 +176——
  因为 2 区末存 2bk 后,41/42 对飞 + 33 楼蓝门换 4yk 的**远端偿还**只在该分支存在。
- 教训:**分区出口规格必须与下游联合求解,不能从单一血统的下游需求反推后当作普适约束**。
  跨区钥匙流(亏在 1-2 区、还在 5 区)要用联合预算搜索,否则局部封闭结论会错杀全局更优。

### 根因 3:收益阈值歧视

6 血、40 血量级的微收益被剪枝/报告阈值过滤,但用户的提升是**一串微收益叠加**
(36 开 2 黄 = 1yk 换 200 血、42 对飞省 40、32 交换省 6……)。搜索报告应保留
「微增益清单」而不是只报最优值。

## 六、存档 route→录像→walk 管线(2026-10-25,重大基建突破)

**存档的 `route` 字段就是全程 .h5route 内层**(LZString 压缩的 token 串,`core.decodeRoute`
可解;与 .h5route 文件的 outer.route 同构)。用户不必手录:任何存档都可以离线还原其
血统的完整录像并转换成 walk。管线(脚本已提升到 `scripts/live/`):

```text
saveNN_slot_raw.json 的 route 字段
  -> scripts/live/build_h5route_from_saves.js(outer={name:"51",version,hard:"",seed:<flags.__seed__>,route}
     经浏览器 LZString.compressToBase64 打包;SEEDS 表按血统填 __seed__)
  -> 首选 scripts/live/capture_ui_replay_cdp.js(被动观察):载入目标存档 →
     游戏 Esc 菜单→同步存档→回放和下载录像→从头回放录像(游戏自己的流程,
     实证干净),钩子只记录;**必须装看门狗**(1.2s 无进度重踢 core.control.replay,
     回放循环靠 handler 自链、会停摆——用户"调最高速"的动作就是在重踢)
  -> 备选 scripts/live/capture_h5route_flags_cdp.js(合成 startGame 回放,带
     容错/自动应答/旗标注入——对 41400 族可用,对跨存档链血统(41228→41477)会
     深脱同步,勿再试)
  -> recording_seed_to_game.py --seed-save <1F种子存档> --capture ... --stage mt4-mt31
     --auto battle=true,item=true,wall=true(无菜单血统)
  -> walk(ok=True, 终态与存档 hero 逐位校验)
```

已成功:capture41→**walk41=41410**(hp41410/dmg13280/g119 与存档41全符)、
capture55→**walk55=653线4F→37F**(MT37 (1,10) hp1166/atk138/def170 与存档55全符)、
capture59→**walk59=41426**(hp41426/g49 全符)。capture57(41477,41228 老存档链)原生回放
**死锁**(route buffer 含 loads 链不连续,容错修不完)——41477 需用户在游戏内对存档57做一次
「设置-同步存档-回放和录像下载-从头回放录像」自洽化后再下载。

管线机制要点(踩坑全集):
1. **血统 RNG 种子 = 存档 flags.__seed__**(41477 族=450161387、41410/653 族=611741486、
   存档1=1352540133),必须传对;不过 zone1 战斗伤害确定,早期状态跨种子一致。
2. **route 头有 SET_AUTO 菜单(help+choices:4)的血统不能预注入 auto**(toggle 会把它翻关);
   无菜单血统(41477 族,auto 由设置 UI 开启、不进 route)必须注入,且要在**每个 action 前
   强制补注**(startGame 后一次性注入会被开局事件异步初始化覆盖)。
3. **鼠标作答的 confirmBox 不进 route buffer**(route 只记 _doReplayAction token)——
   未经「从头回放+下载」自洽化的存档 route 遇到这类框会「录像文件出错」。answer =
   `core.status.event.data.yes/no()` 回调(引擎 choices:N 关不掉 confirmBox);框是
   **异步**打开的,`_doReplayAction` 后检查和 drawConfirmBox 包装都接不住,只能轮询。
4. **失败容错必须包 `_replay_error`**(move/fly handler 内部直接调它:failed=true+错误框+
   replaying=false 三连,外层 hook 全被绕过),且容错分支必须 **setTimeout 手动补拍**
   (引擎靠 action handler 自行调度下一拍,失败的 action 不调度→死循环)。
5. Page.reload 不可靠清钩子(statlog 1×→2×→4×)——用 `location.reload()` + 前置标记验证
   上下文真的换了。**绝不能并行跑两个 capture**(同一页面,后启动的会把先启动的写坏)。

## 七、41426 骨架算子搜索与**模型保真度修复**(2026-10-25 下午,重要)

walk59(=41426,含 36开2黄/42对飞/38F延后 全部用户改进)骨架上跑段交换 2167 变体:
s59_segswap[56,93] = 41522(+96)——MT39 采集段推迟到 zone5 高 def 后拿。

**但 web 验证揭穿了它**:walk59 基线验证在 MT38 (10,1) step 817 失败(gold -90),
statlog 实锤 = **模型 over-sweep**:live 的 auto 收集链是**可被玩家下一拍点击打断的
迭代过程**(41400 原局该 token 链走完 +90 ✓;capture59 原局被打断 +0——同 token
不同结果),模型的单次深 BFS 两处都按走完算。41522 的"+96"正是 over-sweep 在不同
排序下的差分**伪增益**。

**修复(已落地,零回归)**:`Game.auto_sweep` 增加观测预算机制——converter 每个
action 前从 statlog 取**两拍窗口观测差分**(本 token + 下一 token;+4g 这类链尾包干
异步跨拍采样)作为 `_sweep_budget`,auto_sweep 的每次拾取/0-dmg 击杀前预测增益,
超预算则不拾不扩展(该格对 BFS 封锁)。预算维度 = gold/atk/def/yk/bk/rk(hp 被战斗
主导不预算)。重转 capture59:(10,1) 第一访只拿盾(+40def ✓ 与原局打断一致)、
第二访才杀兵(+220 ✓),终态 41426/49 逐位吻合,诊断漂移 ~700→185,6 项回归测试全绿。
**忠实模型下 s59 段交换闭包 = 41426(+96 消失)**——用户 41426/41477 仍是最优,
其段间并无免费的顺序收益。

**工程教训**:① verifier 前必须 `location.reload()`(失败回放的页面残留会让下一次
验证在同一步以不同方式失败——step 5 门步 y9/g4 vs y10/g0 假差异);② sweep 语义
的模型-实机差分只有 web 验证能揭穿(离线 2167 变体的"提升"可以是模型伪影);
③ 任何 walk 产物的 web 验证失败要**先对照 statlog 观测差分**再动手术。

**预算机制的最终状态(当晚定稿)**:观测预算(两拍窗口,converter `--sweep-budget`
实验开关,默认关)能忠实复现"被打断的链"(MT38 (10,1) 第一访只拿盾、重访才杀兵),
但与 verifier 的 settle 式回放**冲突**——回放会让链跑完(MT1 (6,9) 门步 +4g 在回放中
立即完成,而录像里它落在 5 拍之后),打断归因的 walk 永远过不了 settle 式验证。
**未解的核心语义问题**(需专门实机实验会话):web plugin bfs 的收集规则 = 道具远程拾取
+ 怪物何种条件下被清((10,1) 士兵 BFS 可达但链不杀;重访时同链杀)。定论前:
默认转换保持 v1 归因(单次深 BFS,长验证历史),fresh-capture walk 的已知漂移点
(MT38 (10,1) ±90)在验证报告中单列。

**换序算子的粒度(用户修正)**:骨架交换**不应只做相邻对**——至少是**区级
(zone-level)内骨架交换**,且最好是**分析后定向尝试**:先分析两段的收益机制
(哪段的拾取吃哪个 stat 阈值、服务于哪场战斗),再定向交换验证。盲枚举只配做
覆盖性收尾,主搜索必须分析驱动(32F +10 与 31F +0 的对比就是证明:同一类换序,
收益由局部战斗组合决定)。

### B. 为什么之前的 skill 和脚本找不到(五层根因)

1. **模型不忠实(最根本)**:auto_sweep 单次深 BFS 在"链被打断"场景 over-collect
   (MT38 (10,1) ±90)。任何算子在非忠实模型上测出的"提升"都不可信——41522 伪增益
   就是铁证。**修复前一切算子搜索都是噪音发生器**。
2. **算子粒度错配**:32F 交换在 action 列表里不相邻(中间隔整个访问段)——相邻对
   交换(OP-SWAP)覆盖不到;正确的粒度 = 访问段(visit unit)级重排(segswap)。
   而 segswap 又必须有 P5 的 stat 曲线估值(哪段"贵"该后拿),否则只是随机扰动。
3. **单点算子处理联合变更**:P2 推迟需要钥匙流补偿(延后窗口内钥匙缺口由谁还?
   41/42 对飞),单动过推迟必死;P3 门 ROI 需要**终局钥匙盈余**估值(开门收益 vs
   少卖 100G);P7 需要整条购买阶梯换型。我们的算子都是单点 mutation,联合变更
   在单点算子下必然"不可行"。
4. **分区出口规格写死**:vc5/MT9 蓝门定理把 zone1-2 出口规格(yk≥4/bk≥1)从单一
   血统反推后当普适约束,而 41477 的 zone1-2 根(存档2 支)在**该根的下游**有偿还
   通道(2bk→41/42对飞+33楼蓝门换4yk)。跨区钥匙经济必须联合求解,分区规格
   只能作为搜索的候选假设。
5. **搜索种子是我们自己的 walk**:搜索从 41400/41301 的骨架出发,骨架外的
   1F-3F 路径(41228 根的布阵战路线)、zone1-2 根变体从未进入过搜索空间。
   人类 txt 的"逐线终点 diff 表"(本文件第八节)才是最高价值的想法源,但从未被
   机械化成算子。

### C. 改进方案(按优先级,均可落地)

**C0. 忠实模型收尾(前置条件,已完成 80%)**
- 观测预算已落地(`--sweep-budget`)。剩余:plugin bfs 的迭代腿/远程拾取语义实机
  实验定论(道具远程拾取实锤;怪杀条件:(10,1) 可达不杀、重访同链杀——推测=bfs
  只清**移动可达**的 0-dmg 怪,需构造对照实验),然后转正为默认语义。
- 定论后重放 41400/41228/41426 三个已验证 capture 验证零回归,再开算子搜索。

**C1. `lineage_diff.py`(新脚本,最高性价比)**:输入两条 walk/capture → 输出
LCP + 分叉后逐段 stat 归因报告(hp/dmg/gold/yk/atk/def 差异落到具体楼层/怪/门/商店)。
41228↔41477、41426↔41477 的 diff = 优化点账本。**机械化人类的 txt diff 表**——
人肉对比是最强算子,把它变成脚本。

**C2. segswap + stat 曲线估值(P5 正确版)**:访问段重排时,段的价值 =
Σ(其内拾取/击杀在**当前位置属性**下的成本),重排收益 = 移到更高 def/atk 位置后
的战损差。估值需要忠实模型(预算模式)逐段模拟——每个候选 = 完整重放(0.5s,可行)。
适用:zone3-5 的所有采集段。

**C3. 门 ROI 算子(P3)**:对每个未开/已开门,计算「开门收益(门后资源组+捷径省的
路径战损)− 钥匙成本(含少卖 100G 的终局等价)」,按 ROI 排名;与终局钥匙盈余
(41477 只剩 0-2 yk)联合过滤。这覆盖 36开2黄(200+血 vs 1yk)和 33楼蓝门换4yk 类。

**C4. OP-DEFER + 钥匙补偿联合搜索(P2)**:推迟一个转换节点时,同时在**后续 route**
中搜索钥匙缺口的偿还点(对飞/卖钥/蓝门换钥),而不是单点推迟后判死。实现 = 推迟
后跑一次钥匙流可达性检查,把"缺口-偿还对"作为复合候选。

**C5. 跨区钥匙预算求解器(P4)**:zone1-2 出口状态(yk/bk/g)作为变量,zone2 回程
收割消耗、zone4 卖钥收入、zone5 对飞/蓝门偿还作为约束函数,联合搜索(状态空间小:
yk 0-10 × bk 0-4 × g 离散档)。产出 = 各 zone 出口规格的**候选集**而非单一硬约束,
供 segswap/defer 搜索引用。这直接取代"分区出口规格写死"。

**C6. 购买阶梯联合搜索(P7)**:类型(def/atk/hp)× 次数 × 时点的参数化搜索,
生存约束(hp>0)与终局资金悬崖(2120/2420)作为硬过滤。已有参数化购买计划基建
(skeleton_swap 时代),接到新管线即可。

**C7. 人类经验 → 算子的转化纪律(流程性)**:用户 txt 的每条"关键点"= 一个算子
假设。维护第八节对照表;每条新线到手先跑 lineage_diff;每个假设先做**最小可行
验证**(如 32F 交换的插入实验)再决定是否泛化成 sweep——本次 32F(净0)与
41522(伪增益)两个反例证明了这条纪律的价值。
- 对比口径:终局 HP 为主,def/atk 作为辅助列;所有 2420 档选择(血 vs 属性)显式分叉比较。
